## 3. 仕様の確認が要る点
1. **範囲外の入力をどうするか。** limit の 0・負数・小数・上限超え、URI の 0 件や 101 件以上、空の ID、空白だけの検索語を、api.ts は検査せずそのまま送ります。api.ts で弾くのか、バックエンドや Spotify の 400 に任せるのかを決める必要があります。また `type` はエンコードされていない自由な文字列です。
2. **期限切れやセッション消失のとき、どうするか。** api.ts は expires_at を見ません。バックエンドはセッションをメモリに持つので、再起動すると消えます。そのとき返るのは `500 Session not found` です（バックエンドは認証の失敗も 500 で返します）。トークンの削除・再ログインへの誘導・リフレッシュのどれを、どこでやるかが決まっていません。refresh_token は保存されていますが、使われていません。
3. **保存したトークンが壊れているとき。** いまは JSON.parse の生の SyntaxError がそのまま出ます。ほかの場合と同じ「ログインし直して」にするかを決める必要があります。
4. **`VITE_API_BASE_URL` の書き方。** 末尾に「/」があるとパスが `//api/...` になり、バックエンドの受け口と合わなくなる見込みです（実際に動かしてはいません）。この変数は .env.example にも載っていません。
5. **通信失敗とタイムアウト。** fetch の失敗はそのまま投げ直しています（auth.ts は日本語の説明で包んでいます）。タイムアウトはありません。
6. **2xx で本文が空のとき。** 204 だけは `{}` を返し、それ以外は reject します。さらに `{}` は `Paging` などの型と合いません。いまのバックエンドは常に JSON を返すので、実害はありません。
7. **エラー文言。** 既定の文言が `500 Request failed: 500` となり、status が二重に出ます（軽微）。
8. **同じ曲が複数あるときの削除。** URI だけを送るので、Spotify 側では同じ曲がすべて消えます。一方、画面は選んだ 1 行だけを消すので、表示とずれます。
9. **（api.ts の外）101 曲以上のプレイリスト。** 呼び出し側が先頭の 100 曲しか取っていません。

## 4. 今の動きが本来の動きと食い違って見える点
1. **エラー本文が JSON でないと、エラーが別の TypeError に変わってしまう**（[src/api.ts:77](src/api.ts:77)〜83）
   - コードのコメントでは「JSON で読めなければテキストで読む」つもりです。しかし `json()` が本文を読み終えた後なので、`text()` が必ず失敗し、`Body is unusable: Body has already been read` で reject します。status も本文の中身も失われ、console.error も出ません。
   - 起きる場面は、Express が既定で返す 404・500 の HTML、プロキシの 502 などです。
   - 直すなら、先に `text()` で 1 回だけ読んで `JSON.parse` を試す形にします。
2. **removeTracksFromPlaylist の本文がバックエンドと合わない**（[src/api.ts:131](src/api.ts:131)、[backend/src/server.js:286](backend/src/server.js:286)）
   - api.ts は `{ tracks: [{ uri }] }` を送りますが、バックエンドは `uris` を読み、無ければ `400 uris array is required` を返します。そのため、画面の「曲を削除」は必ず失敗するはずです（コードを読んでの判断で、実際につないで試してはいません）。
   - どちらに合わせるかは判断が要ります。Spotify の形に変えるのはバックエンドの役目なので、api.ts を `{ uris }` に直すのが自然です。skip のテストはその前提で書きました。
3. **error が文字列でないと `[object Object]` になる**（[src/api.ts:79](src/api.ts:79)）
   - Spotify と同じ形の入れ子のエラーが来ると、`401 [object Object]` になります。いまのバックエンドは error を必ず文字列で返すので、起きにくい潜在的な問題です。
