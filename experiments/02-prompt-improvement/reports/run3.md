## 3. 仕様の確認が要る点

1. **期限ちょうどのときの扱い**：今は有効です。ただ、画面の `App.tsx` は `expires_at > 今` で判定するので、ちょうどのときは無効扱いになり、画面とサーバーで食い違います。（todo）
2. **Spotify の応答に `expires_in` が無いとき**：期限が NaN になり、そのセッションはいつまでも期限切れになりません。（todo）
3. **`?limit=` のように値が空のとき**：既定値の20を使わず、空のまま Spotify に送ります。fields は空なら付けないので、扱いが揃っていません。（todo）
4. **入力をどこまでサーバーで確かめるか**：今は必須チェックだけで、次のものは Spotify に任せています。
   - range_start などが null や文字列
   - 空の配列、101件以上の uris
   - limit の範囲外の値
   - 中身が空の更新 `{}`
   - 空白だけの name

   このうち「そのまま送る」ことを確かめたテスト（limit 0・51、uris 0・101件、`{}`）は今の動きで書いています。サーバーで弾く方針になったら書き換えが要ります。null の件は todo です。
5. **トークンの持ち方の設計**：
   - access_token と refresh_token を画面にも返していて、画面は localStorage に保存しています。
   - refresh_token は保存するだけで、トークンを更新する仕組みがありません。
   - 期限切れのセッションは、アクセスされない限り消えません。

   テストは今の応答の形で書いています。

## 4. 今の動きが本来の動きと食い違って見える点

どれも今の値はテストで固めていません。確かめられる部分だけを確かめ、残りは todo にしてあります。

1. **画面から曲を消すと必ず400になる**：`src/api.ts` の `removeTracksFromPlaylist` は `{ tracks: [{ uri }] }` を送りますが、サーバーは `{ uris }` を求めています。いちばん影響が大きい点です。
2. **認証エラーが500になる**：x-session-id が無い・不明・期限切れはどれも利用者側の問題なのに、500を返します。`/api/auth/session` は404と401を返すので、揃っていません。テストでは「エラーであること」と「Spotify を呼ばないこと」だけを確かめています。
3. **limit・offset・type をエンコードしていない**：`?limit=5%26market%3DJP` を送ると、Spotify には `limit=5&market=JP&offset=0` が届きました（試して確認）。q と fields はエンコードしているので、漏れに見えます。
4. **id が `..` だと別の Spotify API を呼ぶ**：`/api/spotify/playlists/%2E%2E/tracks` が `.../v1/playlists/../tracks` になり、URL の正規化で `/v1/tracks` を呼びます（試して確認）。自分のトークンでしか呼べないので被害は小さいですが、id の形式を確かめていません。
5. **許可しない Origin に、500とエラーページの HTML を返す**：開発時はスタックトレースも出ます。壊れた JSON を送ったときも同じ HTML（400）で、ほかの `{error}` 形式と揃っていません。
6. **200と201の扱いが逆に見える**：削除と並び替えでは、Spotify が200で返す `snapshot_id` を捨てて `{}` を返しますが、201なら中身を返します。画面は `snapshot_id` を使っていないので、今のところ実害はありません。
