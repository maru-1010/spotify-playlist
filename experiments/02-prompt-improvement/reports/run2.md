## 4. 今の動きが本来の動きと食い違って見える点

**D1：エラー応答の本文が JSON でないと、エラーメッセージが壊れる**（[src/auth.ts:68](src/auth.ts:68)）
- コメントには「JSONパースに失敗した場合はテキストとして取得」とあります。しかし `res.json()` で本文を読み切った後に `res.text()` を呼んでいるため、本物の fetch では `text()` も失敗します。
- その結果、利用者に出るのは「Body is unusable: Body has already been read」で、状態コードもサーバーの文言も消えます。
- 起きる場面は、プロキシが返す 502 の HTML、Q7 の設定ミスで Express が返す 404 の HTML、本文が空のエラー応答です。
- fetch のモックを手作りのオブジェクトにすると、この不具合は隠れてテストが通ってしまいます。本物の `Response` を使ったのはこのためです。

**D2：2xx でも使えない内容の応答を、成功として保存する**（[src/auth.ts:80](src/auth.ts:80)）
- 応答に `session_id` が無い場合や、`expires_in` が無いか 0 の場合でも、ログイン処理は成功で終わります。
- 一方で、App.tsx はそのトークンを「未ログイン」とみなし、api.ts は「Please login again.」で失敗します。コールバック画面ではエラーが出ないので、利用者は理由がわからないままログインできません。
- ログイン済みの状態から再ログインした場合は、使えるトークンが使えないもので上書きされます。
- 今のバックエンドはこれらを必ず返すので、起きるのは想定外の応答が来たとき（バックエンドの版違いや、接続先の設定違いなど）に限られます。
